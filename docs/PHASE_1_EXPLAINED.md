# Celerity Phase 1: learn what we built

## 1. The point of this phase

Celerity will eventually act like a performance engineer: investigate a slow
application, suggest a change, run it, and check whether it helped. Before an
agent can do that, it needs an application to investigate and a way to know the
correct result. Phase 1 builds that application.

The result is a small shopping backend. A backend accepts requests, reads or
changes data, and sends responses. It does not need a shopping website to work.
FastAPI's `/docs` page is our interface for trying it today.

Three switches let us make it perform unnecessary work without changing its
intended answers. Later, agents will need evidence to discover those problems.

## 3. The pieces and their jobs

| Piece | Plain-language job |
| --- | --- |
| Python | The language used to write this phase |
| FastAPI | Receives HTTP requests and connects them to Python functions |
| Pydantic | Checks the shape and allowed values of incoming/outgoing data |
| SQLAlchemy | Lets Python construct database operations and map rows to objects |
| PostgreSQL | Stores products, customers, orders, and relationships |
| HTTPX | Lets our API call the separate shipping service |
| Uvicorn | Runs the FastAPI app and listens for requests |
| pytest | Runs automated checks that behavior remains correct |
| Docker Compose | An alternative way to start the components in containers |

The project-local native database is a convenience because Docker is not installed
on this machine. It is still real PostgreSQL. The Compose files describe the same
application components for a Docker-equipped machine.

The `.venv` folder is a private Python environment for this project. Installing a
package there does not install it into the system Python. `pyproject.toml` describes
our package; `requirements.lock` records the dependency versions used for this build.

## 4. How data is organized

A table is a collection of records of one kind. A row is one record. A column is
one field in that record.

```text
products --------< product_images
    |
    +-------------< order_items >------------- orders >------------- customers
```

`<` indicates the side that can have many records. For example, one order can
contain several order items. Each order item belongs to one product.

| Table | Important information |
| --- | --- |
| products | Name, price in cents, available stock |
| product_images | Product ID and an example image URL |
| customers | Name and unique email |
| orders | Customer ID, totals, status, creation time |
| order_items | Order ID, product ID, quantity, price paid per item |

An ID uniquely identifies a row. A foreign key connects a row to another table:
`orders.customer_id` refers to a valid customer. An order item stores the purchase
price separately from the current product price, so an old purchase retains its price.

Money uses whole-number cents: `1125` means $11.25 in this synthetic USD dataset.
That makes totals exact without using approximate floating-point arithmetic.

The seed creates 2,000 products, two images per product, 1,000 customers, and 30,000
historical orders with one item each. The data is generated by fixed rules, so a
fresh database starts predictably. Image addresses use the reserved `.test` domain;
no real image service is contacted. Current stock is synthetic inventory, not a
replay of all historical purchases.

## 5. Follow a request through the code

For `GET /api/products?limit=3`:

1. Uvicorn receives the HTTP request.
2. FastAPI selects the `list_products` function in `main.py`.
3. FastAPI checks `limit`: it must be between 1 and 100.
4. A database session is opened for this request.
5. SQLAlchemy builds a query; PostgreSQL returns the matching rows.
6. The response is assembled, including each product's images.
7. FastAPI checks/serializes the result into JSON.
8. The session closes, returning the connection for reuse.

A database session is the short-lived workspace for a group of database operations.
An engine manages connections. We create an engine per app, not per request.

`Depends(get_session)` tells FastAPI to supply a session to the route and clean it up
afterwards. `response_model` documents and checks the outgoing data format.

## 6. What happens when an order is created

Try `POST /api/orders` with:

```json
{
  "customer_id": 1,
  "items": [{"product_id": 1, "quantity": 2}],
  "shipping_zone": "national"
}
```

The API checks that the customer and products exist, rejects invalid or duplicate
cart lines, and makes a preliminary stock check. It obtains a shipping quote,
locks the product rows in ID order, and checks stock again. It then calculates
totals using server-side prices, creates an order, and reduces stock in one
database transaction.

A transaction groups changes: either the order and stock changes both succeed, or
neither is committed. On an error, closing the uncommitted session rolls back changes.

A row lock makes another purchase wait before changing the same product's stock.
After waiting, the second purchase sees the updated stock. This prevents two buyers
from both buying the final item. Taking locks in a consistent order also reduces
deadlock risk when carts contain overlapping products.

The shipping request happens before taking row locks so a slow network call does
not hold inventory locks. The preliminary check avoids asking for a quote for a
clearly invalid cart, but it is not enough for correctness: another customer could
buy while we wait. That is why stock must be checked again after acquiring the locks.

Repeatedly submitting a successful order is different from concurrent overselling:
this API does not yet deduplicate repeated submissions. Two identical submissions
can create two orders if stock permits. Adding an idempotency key would address that.

## 7. Fault A: the N+1 query problem

The product list includes images. In the faulty mode:

```text
1 query: read 20 products
20 queries: read images separately for each product
Total: 21 SELECT statements
```

The healthy mode uses `selectinload(Product.images)`:

```text
1 query: read 20 products
1 query: read all their images together
Total: 2 SELECT statements
```

The returned products are identical. What changes is the database work. With small
data or a nearby database, a stopwatch might not show a large difference; query
counts still demonstrate the mechanism. Phase 2 will measure it under controlled load.

In `main.py`, find `list_products`. Then find `Product.images` in `models.py`.
The relationship's default lazy loading means "load these images when accessed."
Accessing that relationship inside a loop is what causes the extra queries.

## 8. Fault B: a missing database index

The order-history route needs a customer's recent orders. An index is an additional
structure that helps the database find matching rows efficiently, much like an index
at the back of a book.

The healthy composite index covers `customer_id`, then descending creation time and
ID. The faulty scenario physically removes this index. PostgreSQL may then scan the
orders table and sort matching rows. Both paths must return the same orders.

`configure_order_index` in `database.py` adds/removes exactly this named index.
`init-db` applies the setting before the app starts. Starting a web process by itself
does not secretly modify the schema.

`EXPLAIN` shows how PostgreSQL plans to answer a query. `EXPLAIN ANALYZE` executes it
and reports what happened. Our reproduction script uses it only on a read query in
the local lab. It does not force PostgreSQL to choose an index.

## 9. Fault C: repeated shipping calls

The shipping stub is a second process. The API asks it for a price over HTTP.
It returns the same deterministic price for a zone. A small configurable delay
models time spent waiting on another service.

- Healthy mode asks once.
- Faulty mode asks three times for the same quote and uses the last result.
- The result remains the same; the repeated requests are unnecessary work.

The API's response header `X-Celerity-Shipping-Calls` reports the configured number.
The tests also count actual HTTP client invocations, so they don't merely trust the header.
The reproduction script counts real outbound requests to the running stub.

`shipping.py` handles outbound calls and validates responses. `shipping_stub.py`
implements the pretend service. Separating them makes it possible to test a failed
or malformed downstream response without contacting a real company.

## 10. Configuration and scenarios

The launcher sets three independent environment variables before starting the app:

```text
CELERITY_ENABLE_N_PLUS_ONE
CELERITY_ENABLE_MISSING_INDEX
CELERITY_ENABLE_REDUNDANT_SHIPPING
```

Named scenarios set one flag, none (`healthy`), or all (`all`). This gives you clean
comparisons. `config.py` reads those values with Pydantic Settings. `.env` contains
local defaults; actual environment variables take priority. Flags are read once
when an app instance starts, so changing scenarios requires stopping/restarting it.

`GET /lab/scenario` shows both the configured flags and the actual index presence.
If they disagree, rerun the initializer with the intended environment before serving
requests. This can happen if you manually start Uvicorn without the launcher.

## 11. How we check correctness

Run from the project folder while PostgreSQL is available:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Tests create a new, randomly named PostgreSQL schema for each database test. A schema
is a namespace for tables inside a database. The test creates and removes only that
namespace, leaving the normal lab tables alone.

The tests check:

- Product contents, pagination limits, and missing records.
- Customer validation and duplicate-email handling.
- Order prices, totals, item quantities, and stock changes.
- Rejected carts and downstream failures leave no partial purchase.
- Two concurrent buyers cannot both reserve the final unit.
- Each fault changes the intended work while keeping the result correct.
- Rerunning the seed does not duplicate data or break generated IDs.

Normal HTTP results include `200` (read success), `201` (created), `404` (not found),
`409` (conflict, such as insufficient stock), `422` (invalid request), and `503`
(a required service is unavailable).

Tests mock the shipping client to make correctness checks fast and repeatable.
The separate `scripts/verify_phase1.py` check uses the real shipping stub and real
PostgreSQL execution plans. It writes evidence to `var/phase1-verification.json`.
Single timing measurements there are illustrative, not a claim of established speedups.

## 12. Read the files in this order

1. `schemas.py`: what requests and responses look like.
2. `models.py`: how those concepts are stored.
3. `main.py`: how a request connects validation, storage, and responses.
4. `shipping.py` and `shipping_stub.py`: a real service boundary.
5. `config.py` and `database.py`: settings and database setup.
6. `seed.py` and `cli.py`: predictable initialization.
7. `tests/`: executable examples of correct and incorrect behavior.
8. `scripts/dev.py`: starting processes and cleaning up processes it owns.
9. `compose.yaml`: the container-based alternative.

## 14. Why this is not the agent phase yet

The future agent will use tools to observe this system, form a hypothesis, try a
change, and verify the result. The deterministic responses and isolated faults give
us ground truth for checking its conclusions. Phase 2 adds systematic measurements;
Phase 3 gives an investigator agent controlled access to diagnostic tools.

This phase gives us the environment in which the agents will learn to operate.
There is no model API key, LLM call, agent team, dashboard, or claimed AI improvement yet.

## 15. GitHub preparation

No remote push is needed for local development. When you ask to publish Phase 1,
the useful source files, tests, docs, Compose file, and CI definition are ready.
`.gitignore` excludes `.env`, `.venv`, `.runtime`, logs, and generated data. Those

checked. Phase 1 should describe a shopping testbed with reproducible faults, not
claim that the future agents already exist.
